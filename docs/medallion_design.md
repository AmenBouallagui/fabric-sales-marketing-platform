# Medallion Design (Bronze → Silver → Gold)

This document is the single design reference for the medallion architecture. The
same Bronze → Silver → Gold logic is implemented three ways in this repo:

- **dbt + DuckDB** — runnable warehouse project in [`dbt/`](../dbt/) (staging → intermediate → marts).
- **Local pandas pipeline** — [`local_pipeline/run_local_medallion.py`](../local_pipeline/run_local_medallion.py).
- **Fabric PySpark source** — [`fabric_notebooks/`](../fabric_notebooks/) (for a future Microsoft Fabric Lakehouse).

The Fabric Lakehouse / Delta deployment itself is a planned step; the dbt and
pandas implementations run today.

## Bronze — Raw + Ingestion Metadata

Bronze preserves source records as-is and adds lineage metadata for auditability,
replay, and future incremental loading. Tables use a `_raw` suffix
(`bronze_customers_raw`, etc.).

Added metadata columns: `ingestion_run_id`, `source_file_name`, `source_file_path`,
`source_system`, `entity_name`, `load_date`, `ingested_at`, `source_updated_at`
(parsed from `updated_at`), and `row_hash` (hash across source columns for
duplicate detection).

In Fabric, source files land in Lakehouse Files using a partitioned convention:
`Files/source/{source_system}/{entity}/load_date=YYYY-MM-DD/file.csv`. Bronze
validation focuses on capture and traceability (required IDs present and non-null,
parseable `source_updated_at`, non-zero row counts, duplicate-ID reporting) rather
than business cleansing.

## Silver — Cleaned, Typed, Deduplicated, Validated

Silver converts Bronze into one trusted current record per business key.

**Standardization:** trim strings; normalize categorical casing (e.g. `Paid`,
`Active`, `In Progress`); cast dates/timestamps; convert boolean-like fields
(`refund_flag`, `is_subscription`); cast monetary fields to 2-decimal numeric and
counts to integers; preserve source business IDs. Adds `silver_processed_at`,
`is_current_record`, `dq_status`, and `dq_issue_reason`.

**Deduplication (latest-record):** partition by business key, keep the row with
the highest `source_updated_at`, then `ingested_at`, then `row_hash` as a stable
tie-breaker. (In dbt this is a `row_number()` window; in pandas, a sorted
`drop_duplicates`.)

**Validation:** each record is flagged `valid` or `rejected` via `dq_status`, with
the reason in `dq_issue_reason`. Only `valid` records feed Gold. Rule details live
in [data_quality_observability.md](data_quality_observability.md).

## Gold — Dimensional Model

Gold turns valid Silver records into a Power BI-ready star schema.

**Dimensions:** `dim_customer`, `dim_product`, `dim_campaign`, `dim_date`,
`dim_customer_segment`, `dim_channel` (the last two conformed for reuse).

**Facts:** `fact_orders` (order grain), `fact_ad_spend` (campaign/day grain),
`fact_support_tickets` (ticket grain). The dbt project prefixes facts `fct_`.

| Fact | Connects to | Key measures |
| --- | --- | --- |
| `fact_orders` | customer, product, campaign, date | quantity, total, net revenue, estimated cost, gross margin |
| `fact_ad_spend` | campaign, channel, date | spend, impressions, clicks, conversions |
| `fact_support_tickets` | customer, date | ticket count, response/resolution minutes, satisfaction |

**Derived order measures:** `net_revenue = total_amount - tax_amount`;
`estimated_cost = quantity * product unit_cost`; `gross_margin = net_revenue - estimated_cost`.

**Surrogate keys:** deterministic keys (hash-based in pandas/Fabric;
`dbt_utils.generate_surrogate_key` in dbt) so reruns produce stable joins. Source
business IDs are kept as alternate keys.

**Unknown members:** each dimension carries an unknown member (`-1` /
`Unknown …`). Facts whose foreign key cannot be resolved point to it, so
referential-integrity tests stay green without dropping fact rows.

**Date dimension:** covers the full span of business dates with `date_key`
(`YYYYMMDD` integer), calendar attributes, and a weekend flag; marked as the date
table in Power BI.

## Validation

Gold validation confirms unique surrogate keys, resolvable fact foreign keys,
non-negative additive measures, date keys covered by `dim_date`, and Silver→Gold
row-count reconciliation for valid/current records. These checks are implemented
as dbt tests (see [`dbt/README.md`](../dbt/README.md)) and as the local pipeline's
observability outputs.
